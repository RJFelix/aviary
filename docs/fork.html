The Fork Line

Prime Agent can split a session and has never once been asked to. Five agents went looking for why, and found something better than an explanation: fork is two one-line changes away from being the most valuable primitive in the harness — and one of those lines is quietly costing money on every session that has nothing to do with forking.

Two lines stand between fork and the best tool in the harness

  1. A directory name. The kernel snapshot path is getSessionArtifactDir(), keyed on session id. A fork mints a new id, so restore looks in an empty directory. Prime Agent serializes your entire Python namespace on the way out of a fork, writes it into the parent’s artifact dir, boots a cold kernel for the child, and never reads the file it just wrote. The restore machinery is already built and correct; only the directory name is wrong.
  2. A line of text. Conversation log: ${messagesPath} sits in the system prompt ahead of 46,713 characters of skill descriptions. It contains the session’s own file path, so it is unique per session — which means no two sessions can share a cached prefix, and a fork pays the full cache write rather than reading its parent’s. This is not a fork bug. It is a store-wide cache leak that fork merely makes expensive enough to notice.

Everything below is downstream of those two. The five explorations disagreed about what to build and agreed, without coordination, that neither of their favourite ideas is safe until the first line is fixed.

Corrected

How fork actually works

Worth stating plainly, because I got it wrong twice — once before this fan-out and once inside the brief I wrote for it. Numbered because it is a real sequence.

  1. A fork creates a new session file. It does not append a branch to the existing JSONL. createBranchedSession(leafId) walks the ancestor path, drops label entries, mints a new id, and writes [newHeader, …ancestorPath, …reparentedLabels]. Forks make a forest of files.
  2. The copied entries keep their original ids. Only labels get fresh ones. So sibling files share entry ids and the fork point is an exact set intersection — no heuristic, no prefix hashing, no model call. Verified
  3. The only link back is parentSession in the new header, alongside a freshly captured git context. The old file is untouched and still complete.
  4. position:"before" requires a user message and returns its text. It branches from that message’s parent — a rewind — and hands back selectedText. The primitive is natively an edit-and-resend. position:"at" is the RPC clone command.
  5. Forking tears down and rebuilds the runtime. New lease, teardownForReplacement("fork", …), new SessionManager, new kernel, new session-artifacts/<new-id>/. On macOS that is a full cold boot — the kernel fork-server is gated on platform === "linux" because fork-without-exec is unsafe on Darwin.
  6. It works on any session file, not just the live one. SessionManager.open(currentSessionFile, sessionDir) — so forking from history is already supported at the runtime level. Verified
  7. Forking the first user message yields an empty prefix. targetLeafId = selectedEntry.parentId can be null, and the runtime then takes newSession() instead. That is a native “start over, rephrased” no UI exposes.
  8. There is a cancellable policy hook nothing uses. session_before_fork fires before any of this. Its result type declares cancel and skipConversationRestore — and skipConversationRestore appears nowhere else in the source. It is a dead field: an extension setting it gets silence. Verified

There is an irony in which field died. Fork carries the conversation and drops the world; the one knob anybody bothered to declare would have let you drop the conversation too.

Nobody would guess these

Three surprises inside the survival table

Forking steals the parent’s cron jobs Verified

Jobs are keyed on activeSessionId — the stable per-attachment id — not on the session file. When the file changes underneath, rebindSessionJobs rewrites every matching job onto the new session and relocates it into the fork’s artifact dir. Its own doc comment says so: “move jobs stored for its stable active session id to the new file so future restores target the current session.”

Correct for resume and switch_session. But fork is the one sibling where the parent file is meant to stand as a checkpoint — and there the same code silently transfers the parent’s schedule and heartbeat to the child. Right by design for three of four cases, wrong for exactly the one you would want to fork.

core/cron-jobs.ts:259 · modes/daemon/daemon-mode.ts:1453

The fork remembers deciding to write the note. It cannot read the note.

Refinement history survives, because it lives in custom entries on the copied ancestor path. Local harness state dies, because it lives in the per-session-id artifact dir. So a forked session inherits a complete record of having taught itself things, and none of the things.

Which also means auto-refine — on by default, every 25 assistant turns — keeps writing into a directory the fork will never read.

agent-session.ts:7808 vs refinement.ts:273

A mid-goal fork spends one budget twice

Goal state is a custom entry on the ancestor path, so it survives — including tokensUsed and the continuation counters, rewound to the branch point. Fork a session with an active goal and you have two live goals, each believing it has the unspent remainder of the same allowance.

core/agent-session.ts:1575–1587

And one gift: the fork point is exactly computable

Because copied entries keep their ids, comparing two siblings is a set intersection rather than a diff heuristic. Every “compare these branches” feature is cheaper here than it would be in a system that re-keyed on copy. branch-summarization.ts already extracts readFiles/modifiedFiles from a common ancestor — the harness summarizes an abandoned in-file branch on tree-navigate and never on fork, so harvesting is a missing call site, not a missing capability.

The finding with a dollar sign on it

One line of text costs the cache everything

The brief I wrote asserted that a fork shares an exact token prefix with its parent, which is precisely the shape prompt caching rewards. That premise is false as built, and the reason is a single line.

core/prompts/rlm.ts:88-100    (buildRlmPrompt — the system prompt prefix)

    `Working directory: ${cwd}`,
    `Conversation log: ${messagesPath}`,     <-- unique per session
    `Recursive agent depth: ${depth}`,
    ...

core/system-prompt.ts:123     prompt = buildRlmPrompt({...})
core/system-prompt.ts:172     prompt += formatSkillsForPrompt(skills)   <-- 46,713 chars

Cache blocks are prefix-hashed. A change ~1k in invalidates everything behind it — so the session’s own file path, sitting upstream of the entire skill catalogue, means the fork does not read its parent’s cache. It writes a fresh one, in full, every time.

What that costs, from the measured 10,883 skill tokens at 62.7% of a 17,357-token input:

Per forkAs a cache read (0.1×)As a cache write (1.25×)
system prompt only, Opus-class$0.026$0.326
system prompt only, Sonnet-class$0.005$0.065
plus a 100k-token ancestor path, Opus-class$0.15$1.88

Two consequences worth separating. The first is about fork: a fork off a long trunk is the harness’s most expensive gesture, and it is expensive in proportion to how much history you wanted to keep — the exact inverse of the intuition. Fix the line and the same fork costs about three cents.

The second is bigger and has nothing to do with forking. Every session’s system prompt is unique before the skills block, so no two sessions on this machine have ever shared a cached skill catalogue. The write is paid 81 times instead of once. Fork just makes the leak expensive enough to see.

Honesty about this numberThe cost table is arithmetic on measured token counts, and the cache-invalidation claim is an inference from how prefix caching works — not a measured hit-rate experiment. The agent that found it proposed the measurement itself: a badge showing cold-boot milliseconds, tokens re-paid, and the actual cached-token count on the first post-fork request. Run that before quoting the dollar figures at anyone.

Decision aid

Fork is the most expensive member of its own family

Walking up one level, fork is a session replacement, and its siblings are newSession, resume and compaction — all four routed through the same teardownForReplacement + buildAndApplyReplacement path. Ordered by what “the context is wrong, do something” actually costs:

MoveNew fileKernelRe-pays 68 skillsCarries
navigateTreenokeptnoeverything; one summarization call
compactionnokeptnoa summary; destroys the rest
rlm('task')yescoldyesthe task string, nothing else
fork / cloneyescoldyesthe entire ancestor path

Read the last two rows together and the rule falls out: fork is strictly dominated by rlm on cost, differing only by the ancestor path. So fork if and only if the history is worth more than re-caching it — which, today, means a lot, and after the one-line cache fix means almost nothing.

The empty branches in that family tree are where the value is: there is no fork that keeps the kernel, and no fork that keeps the session id. And note what else is missing — every other move has an inverse (newSession/resume, compact/expand). Fork has none. There is no merge, and the data model forbids one: an entry has exactly one parentId, a header exactly one parentSession. Every reunion is lossy by construction, so harvesting is not a compromise — it is the only available shape.

Lens 01

Why an impulse never became a command

organon-construction × negation → list · predictability, modularity, cardinality

The explanation for zero forks in 81 sessions, and it is not that fork is useless: the impulse’s half-life is shorter than the command’s activation energy. /fork costs recall, then a picker, then a rebuilt kernel — three deliberate acts to express a one-second thought. A GUI’s advantage is not better forking; it is that the gesture can be ambient: attached to something already on screen, one click, free to abandon.

Its central claim is that the primitive has been mislabelled its whole life. position:"before" refuses anything but a user message and hands back that message’s text — nothing else in the RPC surface returns the argument you are replacing. Fork is an edit-and-resend filed under “branching,” and the filing is why nobody reached for it.

Say It Again S

A hover control on every user bubble that rewinds to just before that turn and drops the original text into the composer, cursor at the end. The primitive’s own shape, drawn.

ObjectionThe gesture’s felt promise is “same situation, different words,” and that promise is false. The kernel dies, a cold one boots, and the variables that made the parent turn productive are gone. A one-click fork that silently discards working state is worse than no fork — it will feel like the agent got dumber, and you will blame the model, not the gesture.

Also found: Aviary’s live transcript mints synthetic ids for user turns (LiveTranscript.swift:32), so no live bubble knows its harness entryId. That is why get_fork_messages is load-bearing rather than convenient.

Lens 02

A lexicon of unbidden forks

tree-finding × negation → dictionary · predictability, source, autonomy

Written as a dictionary of forks nobody asked for — bulwark (clone before a destructive act, so the frozen parent is the restore point), salvage (fork to the last good user message instead of retrying into a poisoned context), heterofork (N branches, N models), taskbranch (a working branch off a long trunk), handoff (the agent emigrating into a clean continuation of itself), thicket (a forest nobody reads).

Its structural point: auto-refine is the existing precedent for autonomous self-modification in this harness — it proves the pattern is tolerable, and it proves the failure mode. Six entries per kind, alphabetical, no prune. An auto-fork policy will fail the same way unless it ships with a reaper.

Bulwark M

Clone before something irreversible, leaving the parent file frozen and complete. Built on the inversion nobody expects: you do not fork to make a spare branch — fork replaces your runtime, so you cannot run two. You clone to become the spare.

ObjectionIt checkpoints the wrong layer. The restore point holds your beliefs, not your filesystem — and the acts you most want a bulwark against (git push --force, terraform apply, a dropped table) are exactly the ones a conversation rewind cannot undo. A restore point that feels like insurance and is not may be worse than none.

Lens 03

The territory a fork walks out of

dimension-identification × cross-domain-reinstantiation → map · rate, connectivity, polarity

This produced the survival table above, then re-instantiated the whole thing in apiculture — a beekeeper’s walk-away split, where the bees are the conversation and everything else is comb. Every answer the domain has evolved is a deliberate carry, never a default: move frames of brood and stores across; requeen or accept the brood break; reduce the entrance so foragers do not drift back to the wrong hive; and do not split during a dearth. The drift is exactly the cron theft. The dearth is exactly the macOS cold boot.

Frame Carry M

After session_start{reason:"fork"}, copy the parent’s snapshot into the fork’s artifact dir and restart the kernel, so the existing resume path revives it. The machinery is built and correct; only the directory name is wrong.

Objection, and it sharpens the fixCarrying the kernel is safe — a dill heap has one writer. Carrying the notes is a split-brain write: two sessions descend from one 6-entry, alphabetically truncated, no-merge list, and both will rewrite it, silently overwriting each other with no ancestry recorded anywhere. So the honest v1 is asymmetric — carry the comb, leave the notes, and say which. The incoherence is not fork’s fault: per-session harness state was never designed to have a second owner.

Lens 04

Coming back

organon-construction × substitution → matrix · direction, predictability, autonomy

A matrix of six diverged things against four verbs reunion could mean — compare, harvest, adopt, retire. Reading it produced the cwd finding above, the observation that reunite(A,B) ≠ reunite(B,A) (only the winner keeps running, only the loser gets summarized — worth surfacing, because “merge” never sounds irreversible and this is), and the empty cell: there is no verb for “both siblings were right.”

Its substitution on direction is the one to steal. Fork today is accumulate-only, structurally identical to the continual harness. Make it decaying instead: a branch carries a TTL and, on expiry, harvests itself into a dated knowledge/ draft. The default outcome of a fork becomes a note, not a file.

Speculative fork instead of rlm L

Fork is the only mechanism in this harness that hands a child the whole conversation at near-zero context cost, while an rlm child starts blind and re-pays 62.7% of input on skills. Fork should be the cheap child.

Objection, and it may be the real productA fork duplicates the transcript but not the world. The sibling boots with a detailed, confident account of a repository its twin is concurrently editing, no kernel state, and no lock — so it acts on stale belief with full conviction, which is worse than rlm’s honest ignorance. Speculative fork is only safe with worktree isolation — and once you add that, the fork has become a worktree agent that happens to remember the conversation, which may be the actual feature.

Lens 05

The price of a fork

tree-finding × dimension-identification → list · visibility, scope, direction

This lens produced the cache finding and the family-cost table above. Its other contribution is the visibility axis: fork spend today is unattributable. The child header records parentSession; the parent is never told it has children. A five-branch exploration reads as five unrelated sessions and nobody sees the $1.60. A cost-control tool that cannot report its own cost is a cost multiplier.

Trunk-and-Branch L

At the compaction threshold, fork instead of compacting: a bounded working branch, a pristine trunk, nothing destroyed. The harness owns a lossless alternative to its lossy default and has used it zero times in 81 sessions.

Objection, and it is about orderingA fork’s cost scales with the trunk you fork from, so auto-forking at the compaction threshold forks at the most expensive possible instant — ~100k tokens of cache write, ~$1.88 Opus-class, plus a cold boot — precisely when compaction would have cost one cheap summarization call. It is not a cost-control tool until the cache anchor ships. After that the same fork costs ~$0.15 and the argument inverts. Order matters more than the idea.

And it killed a property I had asserted: “an abandoned fork leaves no trace” is wrong. hasAssistant is tested over the whole of fileEntries, including the copied ancestor path — so any fork past the first exchange writes its file at fork time, whether or not you ever reply. Speculative forking is not free on disk, and every “ghost fork” design built on that freedom needs rethinking. Verified

Recommendation

What I would build, in order

The ordering is forced by the objections rather than chosen. Three of the five lenses independently concluded that their best idea is unsafe or uneconomic until a prerequisite ships — and the prerequisites are the two one-line changes.

First · the two linesneither is a feature
  1. Stable Cache Anchor. Normalize the Conversation log: line so it is not upstream of the skill catalogue — in the harness, or from before_provider_request without touching it. This is not a fork feature. It is a store-wide cache fix that fork happens to have exposed, and it changes the economics of every idea below. Measure the hit rate before and after; that measurement is Fork Weather, so build them together.
  2. Frame Carry, asymmetric. Carry the kernel snapshot; leave the harness notes; state plainly which. Until this ships, every fork gesture makes the agent look dumber for reasons the user will misattribute to the model.
Then · make forking legibleread-only, files are truth
  1. Forest Ribbon. Render the forest from parentSession headers with the exact divergence point. Transcript.swift already parses parentSession and nothing consumes it, and AgentTree builds edges only from daemon parentSessionId, so forks are invisible even when they exist.
  2. Split Sheet and Goal Twin Guard. Say what a fork will cost you before it costs it — including the stolen schedule and the duplicated goal. Both are a read plus a dialog.
  3. Say It Again. Once the kernel carries, draw the primitive as what it actually is. This is the gesture that decides whether fork gets used at all.
Then · actneeds the meters from above
  1. Entrance Board. Fix the cron theft — or at minimum, stop it being silent.
  2. Harvest to knowledge/, wired to branch-summarization.ts. Reunion is lossy by construction, so build the only shape that exists rather than pretending a merge is coming.
  3. Bulwark, with the caveat on the label. Never call it a restore point; call it a conversation checkpoint, because that is all it is.
  4. Trunk-and-Branch — but only after the cache anchor, and only with a measurement showing a fork at the threshold now costs cents rather than dollars.
Reconsideron this evidence
  1. Ghost Fork, and anything else resting on “abandoned forks leave no trace.” They do leave a file. The design needs a different safety story — probably an explicit reaper rather than a self-erasing child.
  2. Speculative fork as an rlm replacement — not because it is wrong, but because the honest version is a worktree agent that remembers the conversation. That is a bigger and better idea than a fork feature, and it deserves to be scoped as one.
